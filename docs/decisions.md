## Р1. Шрифти та зовнішні ресурси — обидва режими рівноправні

**Рішення:** нічого не «виправляємо». Проєкт свідомо підтримує і мережеві, і локальні ассети.
Команда `templates vendor` знімається з плану як обов'язкова (лишається як опційна зручність
у Кроці 6, не раніше).

Що з цього все ж треба зробити — це зробити поведінку **передбачуваною**, бо
`waitUntil: 'networkidle'` на шаблоні з мертвим CDN зависає до таймауту:

| Налаштування | Дефолт | Дія |
| --- | --- | --- |
| `NETWORK_TIMEOUT_MS` | `15000` | ліміт очікування мережевих ресурсів сторінки |
| `FONT_TIMEOUT_MS` | `5000` | ліміт `document.fonts.ready`; після нього рендеримо як є + `warning` |
| `--offline` / `"options":{"offline":true}` | `false` | блокує всі зовнішні запити (`page.route`) — детермінований рендер, лише локальні ассети |
| `--strict-assets` / `"options":{"strict_assets":true}` | `false` | будь-який провалений запит = помилка `ASSET_LOAD_FAILED`, а не тихий фолбек |

Плюс у результат рендеру додається діагностика — це дешево і рятує від «чому шрифт не той»:

```jsonc
"assets": {
  "requested": 7, "failed": 0, "external": 2,
  "fonts_ready": true,
  "failures": []          // [{url, status, error}]
}
```

У маніфесті шаблону — інформаційне поле `"network": "required" | "optional" | "none"`,
щоб `eavexa templates list` показував, які шаблони працюють офлайн.

## Р2. Робота без Docker — базовий режим. Що таке `result_url`

### Р2.1 Коротка відповідь на питання

**`result_url` — це НЕ місце зберігання. Це посилання на завантаження.**

Два різні поняття, які я в попередньому плані злив докупи:

| Поняття | Що це | Керується |
| --- | --- | --- |
| **Storage** — *куди зберігається* файл | реальне місце на диску або в S3 | `OUTPUT_DIR`, `STORAGE_DRIVER`, `output.type` |
| **Delivery** — *як його забрати* | посилання / шлях / байти у відповіді | `output.type` + режим (sync/async) |

`result_url` — це просто `GET /v1/jobs/:id/result` на самому EAVexa, який стрімить файл
з того місця, де він лежить. Тобто це «ручка» до артефакту, а не сховище.

Питання «звідки взяти абсолютний URL» виникає лише тому, що процес не знає свого зовнішнього
імені — за проксі, у контейнері, за NAT. Раніше я пропонував обов'язкову змінну; це зайве.

### Р2.2 Як формується `result_url` (без обов'язкових змінних)

Пріоритет, зверху вниз:

1. `EAVEXA_PUBLIC_URL`, якщо задано — виграє завжди;
2. заголовки вхідного запиту, який створив джоб: `X-Forwarded-Proto` + `X-Forwarded-Host`, інакше `Host`;
3. якщо джоб створено **не по HTTP** (CLI) — `result_url` = `null`, а доставка йде через `result.path`.

Так у 90% випадків нічого налаштовувати не треба: локальний запуск `eavexa serve` на
`localhost:8080` дасть `http://localhost:8080/v1/jobs/…/result`, бо саме такий `Host` прийшов
у запиті. Змінна потрібна тільки якщо адреса, з якої прийшов запит, ≠ адреса, з якої
webhook-одержувач зможе завантажити файл.

### Р2.3 Форма результату завжди однакова

```jsonc
"result": {
  "type": "video", "mime": "video/mp4", "filename": "promo.mp4", "bytes": 41930210,
  "width": 2160, "height": 3840, "dpr": 2, "duration": 5, "fps": 30, "frames": 150,
  "checksum": "sha256:9f86d081…",
  "storage":  "local",                                  // local | s3 | memory
  "path":     "S:\\Daedalus\\Aureum\\EAVexa\\data\\outputs\\2026-07-25\\j_01JB2K\\promo.mp4",
  "url":      "http://eavexa:8080/v1/jobs/j_01JB2K/result",   // null, якщо джоб з CLI
  "data":     null                                      // base64, лише коли явно попросили
}
```

`path` є **завжди** при `storage: "local"` — і в Docker, і без нього. Це ключ до стратегії
спільного тому (див. Р4.3).

### Р2.4 Що конкретно означає «нормально працює без контейнера»

- [ ] `npm i && npx playwright install chromium && npx eavexa serve` — і все працює, нуль env-змінних.
- [ ] Жодних Linux-специфічних дефолтів (`CHROME_PATH` вже виправляється в Кроці 0).
- [ ] Усі шляхи через `path.join` / `pathToFileURL` — Windows-шляхи з `S:\` і пробілами коректні.
- [ ] `TMP_DIR` за замовчуванням `os.tmpdir()`, не директорія проєкту.
- [ ] `data/` створюється лениво при першому записі, а не при імпорті модуля
      (зараз `RenderJobBuilder` робить `mkdirSync` у конструкторі — прибрати).
- [ ] Ніякого `--no-sandbox` як єдиного варіанту: він потрібен у контейнері, але на хості
      краще без нього → `CHROME_SANDBOX=auto|on|off`, `auto` = вимикати лише коли `/.dockerenv` є.
- [ ] `eavexa doctor` працює на Windows/macOS/Linux однаково.
- [ ] `docs/deployment.md` покриває три сценарії: **bare metal** (systemd unit + Windows
      Task Scheduler/NSSM + pm2), **Docker**, **docker-compose з n8n**.

Docker — це один зі способів запуску, а не передумова. У Кроці 5 порядок пунктів
міняється: спершу bare-metal-інструкція, потім контейнер.

## Р3. Retention — за замовчуванням зберігаємо назавжди

**Рішення:** TTL вимкнено за замовчуванням. Артефакти й записи джобів живуть, доки їх
не видалять явно.

```text
RETENTION_MODE = keep | ttl | consume        (дефолт: keep)
RETENTION_TTL_MS = <ms>                      (діє лише при mode=ttl; дефолт: null)
RETENTION_MAX_BYTES = <bytes>                (опційна межа сховища; дефолт: null)
```

| Режим | Поведінка |
| --- | --- |
| `keep` *(дефолт)* | нічого не видаляється автоматично; `result_url` вічний |
| `ttl` | джоб і артефакт видаляються через `RETENTION_TTL_MS` після завершення |
| `consume` | артефакт видаляється після першого успішного `GET /result`; метадані лишаються |

Наслідки, які треба врахувати в реалізації:

1. **Гонки «n8n не встиг забрати» більше не існує** — це знімає ризик, який я позначав раніше.
2. **Сховище росте необмежено.** Тому обов'язково:
   - розкладка `OUTPUT_DIR/<YYYY-MM-DD>/<job_id>/<filename>` — по датах, щоб директорії
     не мали десятків тисяч записів;
   - `JobStore` — **один JSON-файл на джоб** (`data/jobs/<YYYY-MM-DD>/<job_id>.json`),
     без єдиного індекс-файлу, який довелось би переписувати цілком;
   - в пам'яті — лише LRU-кеш активних джобів, не всі;
   - `GET /v1/jobs` читає з диску з пагінацією (`limit`/`offset`/`before`), а не вантажить усе.
3. **Ручне прибирання як явна дія:**

```bash
eavexa jobs prune --older-than 30d            # видалити джоби + артефакти
eavexa jobs prune --status failed
eavexa jobs prune --keep-last 500 --dry-run
eavexa jobs stats                             # скільки джобів, скільки займають на диску
```

`DELETE /v1/jobs/:id` і `DELETE /v1/jobs?older_than=30d` — те саме по HTTP.

4. `checksum` у результаті дозволяє pipeline перевірити цілісність і робить повторне
   завантаження ідемпотентним.

## Р4. Великі файли назад у n8n — головне рішення

Так, проблеми будуть, і вони конкретні. Розберемо, де саме, і як обійти.

### Р4.1 Де n8n ламається на великих файлах

| Обмеження | Дефолт | Що станеться |
| --- | --- | --- |
| `N8N_PAYLOAD_SIZE_MAX` | ~16 МБ | тіло webhook/запиту більше за це → n8n відкидає з `413`. **Base64 у webhook мертвий на старті.** |
| `N8N_DEFAULT_BINARY_DATA_MODE` | `default` (у **пам'яті**) | бінарник з HTTP Request node тримається в RAM усього виконання; відео на 200 МБ × кілька item-ів → OOM воркера |
| Base64-накладні | +33% | 150 МБ файл = 200 МБ у тілі JSON, плюс парсинг |
| Таймаути ноди | різні | довге завантаження може обірватись без ретраю |

Головний висновок: **байти не повинні проходити через тіло webhook-а, і бажано взагалі
не проходити через пам'ять n8n.**

### Р4.2 Рішення: віддаємо `path` і `url` **одночасно**, завжди

Оскільки за Р3 ми й так зберігаємо артефакти назавжди у власному `OUTPUT_DIR`, файл на диску
є **завжди**. Отже вибирати стратегію доставки наперед не треба — це помилкова дихотомія.

**Правило:** при `storage: "local"` результат і webhook завжди містять **обидва** поля:

```jsonc
"result": {
  "path": "/data/outputs/2026-07-25/j_01JB2K/promo.mp4",   // для локального читання
  "url":  "http://eavexa:8080/v1/jobs/j_01JB2K/result",     // для мережевого завантаження
  "bytes": 41930210,
  "checksum": "sha256:9f86d081…"
}
```

Наслідки:

- Для async **немає що обирати** — n8n бере те поле, яке зручне конкретній ноді, і це
  рішення приймається **у workflow, а не в запиті**. Змінити підхід = переставити ноду,
  а не переписувати виклик API.
- `output.type` звужується до двох ролей: (1) яким буде **тіло синхронної відповіді**,
  (2) чи робити **додаткову** роботу — вивантаження в `s3` або `push`. Для async з локальним
  сховищем він взагалі не потрібен.
- `PERSIST_SYNC_RENDERS` (дефолт `true`) — чи писати на диск також sync-рендери. Можна
  вимкнути для високочастотної генерації картинок, де файли на диску не потрібні.

Це рішення робить `path` дефолтом де-факто, як ти й пропонуєш, але без втрати запасного шляху.

### Р4.3 Важливий нюанс: `path` не рятує від пам'яті n8n при завантаженні

`path` прибирає **один HTTP-хоп і подвійну буферизацію**. Але якщо наступна нода — це
завантаження у YouTube, n8n усе одно має прочитати файл у свій binary-об'єкт, щоб відправити
його. Тобто:

```text
[Read Files From Disk] → binary в n8n → [YouTube upload]
                          ↑ ось тут файл усе ще проходить через n8n
```

Тому **`N8N_DEFAULT_BINARY_DATA_MODE=filesystem` потрібен у будь-якому разі** — і при `url`,
і при `path`. `path` економить трафік і час, але не знімає вимогу до конфігурації n8n.

Де `path` дає максимум, а де — ні:

| Призначення | Як приймає медіа | Найкращий варіант |
| --- | --- | --- |
| **YouTube** | resumable upload, потрібні байти | **`path`** — економить хоп, байти все одно йдуть через n8n |
| **Instagram Graph API** | приймає **публічний URL** (`video_url`/`image_url`), сам його тягне | **`s3` / публічний `url`** — n8n не торкається байтів зовсім |
| **Telegram** | або URL (ліміт ~20 МБ), або upload (~50 МБ) | малі — `url`, великі — `path` |
| **S3 / FTP / Drive** | потрібні байти | **`path`** |
| **Власний API** | залежить | `push` — EAVexa доставить сам |

Тобто для Instagram сценарій «віддати посилання» об'єктивно кращий за «віддати шлях», і саме
тому ми лишаємо обидва поля в кожній відповіді.

### Р4.4 Умови, за яких `path` працює

`path` валідний рівно тоді, коли n8n **бачить цей шлях у своєму просторі імен**:

| Розгортання | Працює? | Що потрібно |
| --- | --- | --- |
| EAVexa + n8n на одному хості, обидва bare metal | ✅ | нічого |
| EAVexa + n8n у docker-compose | ✅ | спільний том, змонтований **за однаковим шляхом** в обох сервісах |
| EAVexa на хості (Windows `S:\…`), n8n у Docker | ⚠️ | bind-mount + `OUTPUT_DIR_ALIAS` |
| Різні машини | ❌ | тільки `url` / `s3` |
| **n8n Cloud** | ❌ | доступу до ФС немає в принципі — тільки `url` / `s3` |

Compose:

```yaml
services:
  eavexa:
    volumes: [ eavexa_out:/data/outputs ]
    environment: [ OUTPUT_DIR=/data/outputs ]
  n8n:
    volumes: [ eavexa_out:/data/outputs ]          # той самий шлях — аліас не потрібен
    environment: [ N8N_DEFAULT_BINARY_DATA_MODE=filesystem ]
volumes: { eavexa_out: }
```

Bare metal (Windows, як у тебе):

```text
OUTPUT_DIR = S:\Daedalus\Aureum\EAVexa\data\outputs
```

n8n на тому ж хості читає цей шлях напряму, аліас не потрібен. Якщо n8n у Docker Desktop —
змонтувати `S:\...\data\outputs` на `/data/outputs` і виставити `OUTPUT_DIR_ALIAS=/data/outputs`.

Ще дві дрібниці, які варто закласти одразу:
- **Права доступу.** У compose образ Playwright працює під `pwuser`, n8n — під `node`
  (обидва зазвичай UID 1000, тож зазвичай усе гладко). Ставимо файлам `0644` явно.
- **Атомарність.** Писати у `<filename>.part` і робити `rename` після завершення — інакше
  n8n може прочитати недописане відео, якщо workflow стартує по вебхуку миттєво.
  `rename` у межах одного тому атомарний, тож це надійно.

### Р4.5 Чотири стратегії доставки

Реалізуємо всі чотири; вибір — через `output.type` у запиті.

#### A. `url` — посилання на завантаження *(дефолт для async)*

Webhook несе `result.url`, n8n другою нодою робить `GET` з `Response Format: File`.

- ✅ працює скрізь, нічого не треба монтувати
- ⚠️ байти проходять через n8n → **обов'язково `N8N_DEFAULT_BINARY_DATA_MODE=filesystem`**
- Вимоги до нашої реалізації `GET /v1/jobs/:id/result` (важливо, не буферизувати!):
  - `fs.createReadStream(...).pipe(res)` — ніколи не `readFile` цілком;
  - `Content-Length`, `Content-Type`, `Content-Disposition: attachment; filename="…"`;
  - підтримка `Range` (`206 Partial Content`) — дозволяє докачку й часткові читання;
  - `ETag` = `checksum`, підтримка `If-None-Match` → `304`;
  - **без gzip** для відео/PNG (`Content-Encoding: identity`);
  - опційний `?token=` одноразовий підписаний токен, щоб URL можна було давати назовні
    без основного `X-API-Key`.

#### B. `path` — спільний том / спільний диск *(найкраще для великих відео)*

EAVexa пише у `OUTPUT_DIR`, webhook несе `result.path`, n8n читає нодою
**Read/Write Files from Disk**. Байти не йдуть по HTTP взагалі.

- ✅ нульове копіювання, немає ліміту розміру, найшвидше
- ✅ працює і в compose (спільний volume), і на bare metal (та сама машина)
- ⚠️ шлях має бути валідним **у просторі імен n8n**. Якщо EAVexa на хості, а n8n у контейнері,
  `S:\…\outputs` для n8n не існує.

Тому додаємо трансляцію шляху:

```text
OUTPUT_DIR        = S:/Daedalus/Aureum/EAVexa/data/outputs      # як бачить EAVexa
OUTPUT_DIR_ALIAS  = /data/outputs                               # як бачить споживач
```

Якщо `OUTPUT_DIR_ALIAS` задано, у `result.path` віддається транслований шлях,
а `result.local_path` лишається реальним. У compose обидва сервіси монтують один том
на `/data/outputs` і аліас не потрібен.

#### C. `s3` — EAVexa сам вивантажує в об'єктне сховище

EAVexa кладе файл у S3/MinIO/R2 і повертає presigned URL.

- ✅ n8n взагалі не торкається байтів — просто передає URL далі (Telegram, YouTube, CDN)
- ✅ найкраще для великих файлів і для горизонтального масштабування
- ⚠️ потрібна інфраструктура

```jsonc
"output": {
  "type": "s3",
  "s3": { "bucket": "media", "key": "stories/{{job_id}}.mp4", "presign_ttl": 86400 }
}
```

#### D. `push` — EAVexa доставляє файл сам

`multipart/form-data` POST на довільний ендпоїнт (у т.ч. на n8n Webhook node з
`Binary Data: true`), або на будь-який API, який приймає файл.

- ✅ обходить n8n як транспорт повністю
- ⚠️ упирається в `N8N_PAYLOAD_SIZE_MAX` одержувача, якщо ціль — сам n8n

```jsonc
"output": {
  "type": "push",
  "push": { "url": "https://api.example.com/upload", "field": "file",
            "headers": { "Authorization": "Bearer …" }, "fields": { "row_id": "42" } }
}
```

#### E. `base64` / `binary` — тільки для малого

`binary` — лише sync-режим. `base64` — тільки коли `bytes < CALLBACK_INLINE_MAX_BYTES`
(дефолт 256 КБ), інакше **автоматичний фолбек на `url`** з полем
`"downgraded_from": "base64"` у результаті. Не мовчазна помилка, а керована деградація.

### Р4.6 Таблиця вибору

Оскільки `path` і `url` віддаються завжди разом (Р4.2), таблиця стосується лише того,
**яке поле брати у workflow** і чи потрібна додаткова робота з боку EAVexa:

| Розмір / ціль | Одна машина / спільний том | Різні машини |
| --- | --- | --- |
| < 256 КБ (PNG), sync | тіло відповіді (`binary`) | тіло відповіді (`binary`) |
| 0.25–20 МБ | `result.path` | `result.url` |
| 20–200 МБ (відео) | **`result.path`** | `output.type: "s3"` |
| > 200 МБ | **`result.path`** | **`output.type: "s3"`** |
| ціль тягне медіа по URL сама (Instagram) | `output.type: "s3"` або публічний `result.url` | те саме |
| n8n Cloud | недоступно | `result.url` / `s3` |

Дефолт при незаданому `output`: sync → `binary` (+ запис на диск), async → нічого зайвого
не робимо, у вебхуку їдуть `path` і `url`.

### Р4.7 Що документуємо для n8n (`docs/n8n.md`)

Обов'язковий блок «Налаштування n8n для великих файлів»:

```bash
N8N_DEFAULT_BINARY_DATA_MODE=filesystem   # критично: бінарники на диск, не в RAM
N8N_PAYLOAD_SIZE_MAX=32                   # МБ, якщо все ж потрібні великі тіла
NODE_OPTIONS=--max-old-space-size=2048
```

І готовий workflow-JSON для обох сценаріїв (`url` і `path`).

### Контракт — уточнення

- `output.type`: `binary` \| `base64` \| `url` \| `path` \| `s3` \| `push` — **один блок**
  замість колишнього роздвоєння `output` + `callback_include`.
- `callback_include` прибирається; його роль виконує `output.type`.
- `result` завжди містить `path`, `url`, `checksum`, `storage`, `bytes` (зайве = `null`).
  **`path` і `url` заповнюються одночасно** при `storage: "local"` — вибір робиться
  у workflow, а не в запиті (Р4.2).
- Запис артефакту атомарний: `<name>.part` → `rename`.
- `PERSIST_SYNC_RENDERS` (дефолт `true`) — чи зберігати на диск також sync-рендери.
- Новий код помилки: `ASSET_LOAD_FAILED`, `RESULT_GONE` (артефакт видалено retention-ом),
  `DELIVERY_FAILED` (для `push`/`s3`).

### Кроки — коригування

- **Крок 1:** `storage_adapter.js` одразу з `local` + аліасом шляху; `render_request.js`
  знає всі шість `output.type`; діагностика ассетів у результаті.
- **Крок 3:** прибрати логіку TTL-видалення; додати `RETENTION_MODE`; webhook з CLI
  віддає `path` (бо `url` = `null`).
- **Крок 4:** `GET /result` — стрімінг + `Range` + `ETag` + опційний `?token=`;
  `GET /v1/jobs` з пагінацією по диску.
- **Крок 5:** спершу bare-metal (systemd / Windows service / pm2), потім Docker;
  `docs/n8n.md` з блоком про великі файли.
- **Крок 6:** `s3` і `push` драйвери, `jobs prune`, опційний `templates vendor`.

Оцінка не змінюється: **≈ 7–9 днів**, придатне до вжитку після Кроку 2.
